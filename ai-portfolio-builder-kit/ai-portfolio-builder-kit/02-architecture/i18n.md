# Internationalization (i18n)

Only if the portfolio is bilingual. A lightweight, type-safe approach — no heavy i18n library needed for a portfolio.

## The dictionary

One `translations.ts` with a nested object keyed by language, and a `t(key)` lookup. TypeScript derives the valid keys from one language so a missing/typo'd key is a compile error.

```ts
export const translations = {
  en: {
    nav_home: 'Home',
    nav_works: 'Projects',
    cs_back_works: '← Projects',
    diagram_process_step_review: 'Design Review',
    // …
  },
  es: {
    nav_home: 'Inicio',
    nav_works: 'Proyectos',
    cs_back_works: '← Proyectos',
    diagram_process_step_review: 'Design Review',
    // …
  },
} as const;

export type Language = keyof typeof translations;           // 'en' | 'es'
export type TranslationKey = keyof typeof translations.en;  // union of keys
```

The `ThemeContext` exposes `t: (key: TranslationKey) => string` bound to the active language.

## Longer content as data functions

For case studies and other long content, don't cram paragraphs into the flat dictionary. Use a function that returns the right dataset:

```ts
export function getCaseStudies(lang: Language): CaseStudy[] {
  return lang === 'en' ? CASE_STUDIES_EN : CASE_STUDIES_ES;
}
```

## Naming keys — a privacy note

**Key names ship in the bundle.** A key like `diagram_acmecorp_caption` leaks a real project name (`acmecorp`) to anyone reading the built JS. Name keys by **function**, not by the real project: `diagram_process_caption`, not `diagram_<clientname>_caption`. This is a real anonymization surface people forget — see `04-content-and-anonymization/anonymization-protocol.md`.

## Rules

- Keep both languages in sync; a key present in one but not the other is a bug.
- Don't machine-translate the case-study voice blindly — the tone matters; review it.
- Alt text, captions, ARIA labels, and metadata all go through `t()` too, so the whole experience switches language, not just visible body text.
